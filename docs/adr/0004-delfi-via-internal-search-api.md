# Delfi integrates via its internal search API, not a headless browser

ADR 0003 deferred Delfi because its product pages are a client-rendered SPA with nothing in the raw HTML — that part is still true. But its *search box* turned out to call a real, unauthenticated internal JSON endpoint (`pc-frontend-api/search/quick-search-products/{category}/{query}`) that returns full product data — title, author, price, live availability, format — in one call, with no separate product-page fetch needed at all.

This was found by loading the real site in a headless browser once, during development, and recording which network request the search box actually fired — not by guessing endpoint names (several plausible guesses, e.g. `pc-frontend-api/book?id=`, returned the same generic homepage payload regardless of parameters). Playwright was a one-time investigation tool here, not a runtime dependency: `DelfiClient` uses plain `httpx`, like Laguna and Vulkan.

This also makes Delfi's integration simpler than the other two: since the search actually works, `DelfiClient` doesn't need the sitemap-cache-and-shortlist approach used for Laguna/Vulkan (see `stores/base.py`) — it implements `find_editions()` directly with a single live search call.

## Update: the `{category}` segment matters, and "all categories" isn't safe

The `{category}` placeholder above isn't decorative — the endpoint's ranking is scoped by it, and it's capped at a handful of results per call. Querying `Sve kategorije` ("all categories") ranks across Delfi's *entire* catalog, not just books: for a heavily-merchandised franchise (mugs, stickers, plushies, earbuds...), real books can be crowded out of the results entirely, e.g. searching "harry potter" or "gospodar prstenova" (Lord of the Rings) under `Sve kategorije` returned zero books.

Probing the category segment with known Serbian category names found two that reliably return actual books: `Knjiga` (domestic) and `Strana knjiga` (foreign/translated) — no combined-category value works, so `fetch_book_editions()` queries both concurrently and merges, deduping by product URL. Both the availability check (`find_editions`) and free-text search (`search_titles`) build on that function: search discovery goes through `search_books()`, which filters `fetch_book_editions()`'s raw candidates by title-or-author relevance (via `matches_query`) without gating on availability, since out-of-stock books should still be discoverable via search — mirroring Booka's `search_books()` (ADR 0009).

## Update: the client hierarchy was split

`BookstoreClient` originally *was* the sitemap-catalog pipeline, so `DelfiClient` had to declare a `_parse_product_page()` that raised `NotImplementedError` — a method it never uses. That machinery now lives in `CatalogBookstoreClient` (Laguna, Vulkan); `BookstoreClient` declares only `find_editions()` and `search_titles()`, which `DelfiClient` implements directly. The stub is gone, and Delfi's search discovery is reachable through the same interface as every other store rather than a module-level `search_delfi_books()` wrapper.

## Update: the query segment is parsed as Lucene syntax, so punctuation is stripped

The endpoint doesn't treat `{query}` as literal text — it hands it to a Lucene-style query parser, and answers HTTP 500 (`SERVICE UNAVAILABLE`) whenever the result isn't valid query syntax. That is not a rare edge: the title `Mona Lisa Overdrive (The Neuromancer Trilogy` (an Open Library record with an unbalanced parenthesis) made every Delfi check fail, and omnibus titles like `A / B / C` failed too, because `/` opens a regex literal. Live probing of the endpoint sorted the characters into three groups:

- **Always unsafe** — `( ) { } [ ] " \ /` (grouping, quoting, escaping, regex) and `^` (boost, which also wants a number after it). Stripped anywhere in the query.
- **Operators** — `+ - ! :` bind to the term that follows them. A query *ending* on one is the HTTP 500 above, but the more dangerous failure is quieter: mid-query they parse fine and **negate**, so the endpoint answers 200 with the wanted book missing from the results. `Hobit! ilustrovano izdanje` and `Hobit -ilustrovano izdanje` both return zero hits where `Hobit ilustrovano izdanje` returns the book. That surfaces in the UI as a clean "Not available", which is a *different* outcome from a failed check (CONTEXT.md) — i.e. the app would confidently report a wrong answer. So the rule is uniform per whitespace-separated token, not just at the end of the query: strip `+ - ! :` from the **start** of every token, strip `! :` from the **end** of every token, drop any token left empty. Probed, so a future reader does not re-litigate either direction:
  - Negating and therefore stripped: `-Hobit ilustrovano izdanje`, `Hobit -ilustrovano izdanje`, `Hobit +ilustrovano izdanje`, `Hobit !ilustrovano izdanje`, `Hobit! ilustrovano izdanje`, `Hobit + ilustrovano izdanje`, `Hobit : ilustrovano izdanje`, `Hobit ! ilustrovano izdanje`, `Hobit - - ilustrovano izdanje` — all 200, all zero hits.
  - Harmless and therefore **kept**: a word-final `-` or `+` (`Hobit-`, `Hobit+`, `C++` → 15 products where `C` → none), intra-word punctuation (`Jean-Paul Sartre` finds the book, `Jean Paul Sartre` finds nothing), and a word-attached `:` (`Hobit: ilustrovano izdanje` still returns the book). A *single* standalone `-` mid-query (`Hobit - ilustrovano izdanje`) was probed and is harmless too — it is dropped only because an operator-token carries no searchable text, so removing it cannot cost recall, and doubling it (`- -`) does negate.
  - Mid-query `:` costs no recall either: six real Delfi-stocked titles containing `:` returned the same result count with and without the colon (1 vs 1 each). It does *not* behave like a Lucene field query here, so only a leading or word-final `:` is removed.
- **Harmless** — `& | ~ * ?` returned 200 in every position probed, so they are left alone.

Percent-encoding was tried first and does not help: the backend decodes the path segment before parsing it, so `%2F` still reaches the parser as `/`. The characters have to be removed, not escaped — which costs nothing, since results are matched against the Book locally afterwards (`matches_book` / `matches_query`), not by the endpoint's own relevance. A query left empty by stripping skips the request entirely rather than sending a bare path segment, which is a 404 and would otherwise surface as a failed check (ADR 0005) when there was nothing to check.
