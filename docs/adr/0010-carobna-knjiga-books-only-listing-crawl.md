# Čarobna knjiga: books-only via genre-page crawl, not sitemap or live search

Čarobna knjiga is a custom-built platform ("Developed by weboperater" in the footer, no WooCommerce/Shopify markers). It does have a working live search endpoint (`GET /pretraga/<query>`, plain server-rendered HTML, no cookies/session required) — but that endpoint returns only title/image/link per result, no price/stock/author, so it doesn't offer the single-call advantage that justified Delfi/Booka's direct-API shape (`BookstoreClient` implemented directly, no catalog). Every candidate still needs its own product-page fetch regardless of how it was discovered. More importantly, `/pretraga` results are **not** scoped to books — querying "betmen" returns comic issues alongside anything else matching — so adopting it would not by itself solve the books-only requirement below; it would just add a second data source on top of whatever solves that problem. `CarobnaKnjigaClient` therefore stays on the sitemap-and-shortlist shape (`CatalogBookstoreClient`, as used by Laguna/Vulkan) and does not use `/pretraga`.

The site's own sitemap (`/sitemap.xml`) is a single flat list of 600+ URLs with no distinguishing prefix: book, comic, and manga product pages sit at the same unprefixed root level (e.g. `/prah` is a book, `/apsolutni-betmen-1` is a comic), interleaved with author pages, category pages, and admin pages. The product pages themselves are templated identically for books, comics, and manga — same `h1.heading-2` title, same "Autor:"/"Žanr:" fields, no breadcrumb or department marker like Vulkan's `_is_book_department` relies on, and no `application/ld+json` structured data at all (unlike Laguna/Vulkan). There is no reliable per-URL or per-page signal to exclude comics/manga from either the sitemap or `/pretraga`'s results.

The site's own genre taxonomy is split by content type at the page level: every genre listing page (e.g. `/fantastika`, `/betmen`) contains products of one type only — confirmed by fetching a sample of genre pages and checking their listings contained zero cross-type slugs. There is, however, **no reliable slug- or markup-level signal** for telling a book genre from a comic genre from the slug alone: some comic genres do carry a `-strip`/`u-stripu` suffix (`/fantastika-u-stripu`, `/horor-strip`, `/sf-strip`, ...), but several others don't (`/betmen`, `/dedpul`, `/dc-mejnstrim`, `/dc-krosoveri`, `/black-label`, `/superherojski-elseworlds`, `/zemaljski-marvel`, `/kosmički-marvel`) — a suffix-based rule would silently misclassify those as book genres. The `/zanrovi` genre index page (which lists all 33 genres, each with its own product count) has no heading, wrapping container, or other DOM marker separating the 13 book genres from the 20 comics genres and 1 manga genre either — they're one flat, undifferentiated list, ordered book-genres-first, comics-genres-next, manga-last, with nothing but that ordering to go on.

So `BOOK_GENRE_SLUGS` in `carobna_knjiga.py` is a hand-verified, hardcoded list of the 13 book genre slugs, built by fetching every genre listed on `/zanrovi` and checking its own product listing by hand (book titles vs. known comic/manga series). This needs a manual update if the site adds a new book genre later — same maintenance cost as Laguna's `_is_book_url` path-prefix rule or Vulkan's `_is_book_department` breadcrumb check, just derived from content-checking instead of a structural marker. Each book-genre page paginates (`ul.pagination`, e.g. `/fantastika/2`) and `CarobnaKnjigaClient` crawls all of them (deduplicating URLs across genres, since a book can be tagged into more than one) rather than the sitemap or `/knjige` (which turned out to be a landing/hub page with a featured carousel, not a paginated grid — the initial candidate approach) or `/hronoloski` ("all books chronologically", which despite its name also mixes in comics — confirmed by inspecting its listing). This gets books-only scoping from the site's own per-genre-page categorization, rather than guessing from weaker signals (e.g. a publisher-imprint logo) that would risk silently leaking comics/manga through and undermining the books-only decision. The cost is more one-time HTTP calls when the catalog is (re)built, which is acceptable since, like Laguna/Vulkan, the catalog is cached and refreshed rarely (`catalog_cache_ttl_hours`), not fetched per search. Comics and manga are out of scope entirely for now — not queryable even by title — and may be added later as a separate integration if there's demand.

Price is read as the discounted "Vaša cena" figure (not the struck-through "Puna cena" list price) — the site shows both, and only the discounted one reflects what a buyer actually pays.

## The base class gained a hook

`CatalogBookstoreClient._get_catalog()` used to hardcode "fetch `self.sitemap_url`, parse as sitemap XML." That doesn't fit a paginated-genre-page-crawl catalog source. The sitemap-fetch-and-parse step was extracted behind an overridable hook (`_fetch_catalog_urls`), with a default implementation reproducing the original sitemap behavior exactly — so `LagunaClient` and `VulkanClient` needed no changes and their existing tests passed unmodified. `CarobnaKnjigaClient` overrides just that hook to crawl the book-genre pages instead.
